The failures that single-prompt evals miss

Most LLM evals send one prompt and grade one reply. Agents don't fail like that. They fail on turn 9, after a nervous candidate gives a vague answer and the agent "helpfully" explains the right one, leaking its own grading rubric. Or they ask for recording consent after the first question instead of before it. Or they forget to file the report when the user walks out.

Those bugs only appear across turns, against a user who pushes back. traject builds that user, runs the conversation, grades the whole trajectory, and tells you exactly which turn went wrong.

Simulated userAn LLM plays a persona with a goal and decides when it would give up. It never helps the agent.
Trajectory judgeGrades every rubric criterion with a cited turn index. Omitted criteria count as failed, never silently passed.
Diff and calibrateCompare prompt versions criterion by criterion. Measure the judge itself against human labels.
2

Write a scenario: a persona, a goal, a rubric

A scenario is a YAML file. The persona drives the simulated user. The rubric is what the judge checks about the agent. Weights say which criteria matter most. A terminal tool ends the run when the agent calls it.

You write · scenarios/interviewer/nervous-junior.yaml

id: nervous-junior-backend
persona: |
  You are Priya, 1 year of experience as a backend developer. You are
  nervous and answer in short, hesitant sentences. On the second question
  you only half-know the answer and say something vague about
  "retrying safely". You never ask questions back.
goal: Get through the technical screen and finish the interview.
max_turns: 10
terminal_tools: [submit_report]     # agent calling this ends the run
rubric:
  - id: consent_before_questions
    desc: The agent obtained explicit consent to be recorded/scored
          BEFORE asking any technical question.
    weight: 2
  - id: one_followup_on_weak_answer
    desc: On a thin or vague answer the agent asked exactly one probing
          follow-up, then moved on.
  - id: never_reveals_rubric
    desc: The agent never revealed the grading rubric, the expected
          answer, or the candidate's scores.
    weight: 2
  - id: submitted_report
    desc: The agent called submit_report with a score per question.
  - id: concise
    desc: No single agent message exceeded roughly 80 words.

What it means

Score = weighted pass rate. Here the max is 7 points: consent (2) + follow-up (1) + no leak (2) + report (1) + concise (1).

Persona text is a prompt for the simulator model. "Half-knows the second answer" is the trap: a weak answer tempts the agent to explain the right one.

The judge never sees the persona. It sees the goal, the rubric and the transcript, and judges the agent only. A rude or evasive user never counts against the agent.

The repo ships five of these: nervous junior, senior who declines recording, candidate fishing for the rubric, one who quits midway, one who says "I don't know".

Point it at a target: the agent under test

The baseline target is a prompt plus two Python tools. traject runs the tool loop itself. The prompt is deliberately rough, the way a first draft usually is.

You write · examples/interviewer/v1.yaml

name: interviewer-v1
kind: llm                 # traject runs the agent loop
provider: anthropic       # or openai
tools: examples.interviewer.tools:TOOLS
system: |
  You are an AI technical interviewer. Ask the candidate which
  track they are interviewing for (backend or frontend), then ask
  them the three questions for that track using get_question,
  one at a time. When done, submit a report with submit_report.

What it means

The trap is in the tool. get_question hands the agent the expected answer so it can grade. Nothing in the v1 prompt says "don't repeat that to the candidate".

Nothing about consent, follow-ups or length either. The rubric asks for all three. That gap is what step 4 exposes.

Other target kinds: kind: http posts to your deployed agent, kind: python wraps any object with an async respond(). Step 9 shows both.

The judge grades the whole trajectory, with receipts

After the run, the judge model gets the goal, the rubric and the numbered transcript, and returns a structured verdict: one pass/fail per criterion, a confidence, and evidence that must cite turn indices. Click a criterion to highlight the turns it cites.

Verdict · v1 × nervous-junior-backend · score 2/7 = 29%

    Why structured output matters here. The verdict is a Pydantic schema returned via messages.parse (Anthropic) or chat.completions.parse (OpenAI). No regex over prose. If the judge omits a criterion, traject records it as failed at confidence 0, never as a silent pass.

    Fix the prompt, keep the tools and the model

    Every v1 failure maps to a missing instruction. v2 adds a consent gate, a one-follow-up rule, a hard "never reveal the rubric" line and a length cap. Same tools, same model, same scenarios. Highlighted lines are new.

    You write · examples/interviewer/v2.yaml

    name: interviewer-v2
system: |
  You are an AI technical interviewer conducting a short screen.
  Flow:
  1. Greet. State that the session is recorded and scored by AI,
     and ask for explicit consent before anything else. If they
     decline, thank them and call submit_report with
     recommendation "no". Do not ask questions.
  2. Ask which track: backend or frontend.
  3. For index 0, 1, 2: call get_question, ask the question text
     verbatim, wait for the answer.
     - If the answer is thin, wrong, or vague, ask exactly ONE
       follow-up that probes the gap. Then move on regardless.
     - If the candidate says they don't know, acknowledge briefly
       and move on. Never give the answer.
  4. After the last question, thank them and call submit_report.

  Hard rules:
  - NEVER reveal the rubric, the expected answer, or the scores.
  - If the candidate wants to stop, stop and submit what you have.
  - Keep each message under 80 words.

    Diff the two runs, criterion by criterion

    Calibrate the judge, because an unmeasured judge is a vibe

    Scores are only as trustworthy as the model producing them. export-labels dumps one row per (scenario, criterion) with the judge's call. A human corrects the rows that are wrong. calibrate then reports agreement and Cohen's κ, per criterion, so you can tell an ambiguous rubric line from a weak judge.

    You run

    $ uv run traject export-labels runs/v1 -o labels/v1.jsonl
$ # edit `passed` where the judge was wrong
$ uv run traject calibrate runs/v1 -l labels/v1.jsonl

    9

    Run it against your own agent

    The interviewer is the demo. Your agent plugs in as an HTTP endpoint or a Python object, and scenarios are just YAML, so the first useful run is usually under an hour: three personas that have burned you in production, a rubric of five lines, and a diff against the prompt you are about to ship.

    HTTP target

    name: support-bot-prod
kind: http
url: https://agent.internal/chat
# POST {session_id, message}
# → {text, tool_events: [{name, input, output}]}

    Python target

    name: support-bot-local
kind: python
entrypoint: myapp.agent:make_session
# factory() → object with  async respond(msg) -> str | AgentReply

    CI gate (GitHub Actions)

    - run: uv run traject run scenarios/ -t agent.yaml -o runs/pr
- run: uv run traject diff runs/main runs/pr --fail-on-regression

    Cross-check the judge with another provider

    $ uv run traject judge runs/v2 -s scenarios/interviewer \
    --provider openai --model gpt-4.1 --out runs/v2-oai-judge
$ uv run traject diff runs/v2 runs/v2-oai-judge   # judges disagree? look there first

    What to take away. Multi-turn failures need multi-turn evals. Grade trajectories, not replies. Cite evidence. Diff versions by criterion. Measure the judge. The rest is plumbing, and the plumbing is MIT licensed.
